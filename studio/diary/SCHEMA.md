# The Studio Diary — schema

A **structured, reusable** build-diary format for the Studio. It is the single
**machine-readable source** of two things at once:

1. **ENTRIES** — a chronological build log (what changed, why, and which systems it touched).
2. **SYSTEMS GRAPH** — the typed node/edge graph of how all the Studio's systems interact.

`diary.json` conforms to this schema. `DIARY.md` is a human render of the entries
(regenerated by `gen-diary.mjs`). The interactive visualizer
(`../tools/sysmap/`) consumes the graph + entries directly.

The format is **engine-agnostic** and **reusable**: any project keeps a `diary.json`
with the same top-level shape; only the node `kind`s and edge `rel`s below are the
fixed vocabulary.

---

## Top-level shape

```jsonc
{
  "project": "string",          // studio / game / repo name
  "generated": "ISO-ish note",  // free text — when/how this file is maintained
  "tiers": [ Tier, ... ],       // the stack the project is organised into (ordered base -> top)
  "entries": [ Entry, ... ],    // (a) the chronological log
  "graph": {                    // (b) the systems graph
    "nodes": [ Node, ... ],
    "edges": [ Edge, ... ]
  }
}
```

`tiers`, `entries`, `graph.nodes`, and `graph.edges` are all **required arrays**
(may be empty, but the keys must be present). A conforming file MUST have
`entries`, `graph.nodes`, and `graph.edges`.

---

## (a) ENTRIES — the chronological log

Each entry records one build phase / commit. Newest-last or newest-first is fine;
`gen-diary.mjs` sorts by `id`.

```jsonc
{
  "id": "e01",                  // string, unique, sortable (e00, e01, ... or a date+seq)
  "date": "2026-06-08",         // ISO date (YYYY-MM-DD)
  "phase": "Phase 0",           // human phase label (e.g. "Phase 1", "Lego")
  "title": "string",            // one-line headline
  "what": "string",             // what was built/changed (1-3 sentences)
  "why": "string",              // the motivation / problem it solves
  "systems": ["spike", "harness"],  // node ids (graph.nodes[].id) this entry touched
  "validator": "string|null",   // how it was proven (a capability id, a command, or null)
  "status": "shipped",          // one of: shipped | green | done | wip | spike
  "artifacts": ["spike/out/scorecard.json"],  // paths/URLs produced (relative to studio root)
  "commit": "f3d2a1a"           // short git SHA (or null)
}
```

| field       | type         | req | notes |
|-------------|--------------|-----|-------|
| `id`        | string       | yes | unique + sortable; the visualizer + DIARY order by it |
| `date`      | string       | yes | `YYYY-MM-DD` |
| `phase`     | string       | yes | groups entries on the timeline strip |
| `title`     | string       | yes | headline |
| `what`      | string       | yes | the change |
| `why`       | string       | yes | the motivation |
| `systems`   | string[]     | yes | each MUST be an existing `graph.nodes[].id` (referential integrity) |
| `validator` | string\|null | yes | the proof: a capability id (`gate`), a command, or `null` |
| `status`    | enum         | yes | `shipped` \| `green` \| `done` \| `wip` \| `spike` |
| `artifacts` | string[]     | yes | produced files / live URLs (relative to `studio/`); `[]` if none |
| `commit`    | string\|null | yes | short SHA, or `null` |

## (b) SYSTEMS GRAPH

A typed graph of the systems and how they interact. The visualizer colors nodes by
`kind`, groups/positions them by `tier`, and styles edges by `rel`.

### Tier

```jsonc
{ "id": "evaluation", "order": 5, "label": "Evaluation", "color": "#e0b341" }
```

| field   | type   | req | notes |
|---------|--------|-----|-------|
| `id`    | string | yes | referenced by `Node.tier` |
| `order` | number | yes | 1 = base of the stack … N = top (drives the tier-stack layout) |
| `label` | string | yes | display name |
| `color` | string | no  | hex; the visualizer falls back to a kind palette if absent |

The Studio's canonical tiers (the book's 7-tier stack, base → top):
`foundations`(1) · `platform`(2) · `engine`(3) · `content`(4) · `evaluation`(5) ·
`feedback`(6) · `publish`(7).

### Node

```jsonc
{
  "id": "feel",               // unique slug; referenced by entries[].systems + edges
  "kind": "validator",        // see KINDS below
  "label": "Studio.Feel",     // display name
  "tier": "evaluation",       // a tiers[].id (which layer of the stack it lives in)
  "validator": "feel",        // a capability id in the Lego registry, or null
  "desc": "string"            // optional one-line description (shown in the tooltip)
}
```

| field       | type         | req | notes |
|-------------|--------------|-----|-------|
| `id`        | string       | yes | unique slug |
| `kind`      | enum         | yes | one of the KINDS below — drives node color |
| `label`     | string       | yes | display name |
| `tier`      | string       | yes | a `tiers[].id` — drives grouping / the tier-stack layout |
| `validator` | string\|null | yes | a Lego registry **capability** (e.g. `gate`, `feel`, `sprite-animation`, `contraption`, `music`) whose pass/fail status the visualizer pulls from `registry.json`; or `null` for nodes without one |
| `desc`      | string       | no  | tooltip detail |

**KINDS** (the node-color vocabulary):

| kind           | meaning |
|----------------|---------|
| `tier`         | a stack layer itself, as a node (optional; tiers are also their own array) |
| `sdk`          | a Studio SDK module (`sdk/studio.js`) — Materials, Textures, Juice, Platformer, Feel, … |
| `tool`         | a standalone tool/brick (`tools/*`) — sprite-studio, contraptions, eval-feel, … |
| `game`         | a game built on the SDK (`games/*`, `game-template`) |
| `validator`    | a gate/checker capability (the AI playtester surface) |
| `orchestrator` | a sequencing/driving system (conductor, dispatcher, registry, forge) |
| `concept`      | a method/contract/doc (the harness method, the tool contract, a spike) |

### Edge

```jsonc
{ "from": "ember", "to": "sdk", "rel": "depends-on" }
```

| field | type   | req | notes |
|-------|--------|-----|-------|
| `from`| string | yes | a `graph.nodes[].id` |
| `to`  | string | yes | a `graph.nodes[].id` |
| `rel` | enum   | yes | one of the RELATIONS below — drives edge style |

**RELATIONS** (the edge-style vocabulary, read `from` → `to`):

| rel            | reading | example |
|----------------|---------|---------|
| `depends-on`   | from needs to | `ember` depends-on `sdk` |
| `validated-by` | from is gated by to | `sprite-studio` validated-by `sprite-animation` |
| `dispatched-by`| from is invoked through to | `sprite-studio` dispatched-by `dispatcher` |
| `feeds`        | from supplies input to to | `conductor` feeds `dispatcher`; `levels` feeds `feel` |
| `produces`     | from creates to (an artifact/output) | `sprite-studio` produces `sprite-sheet` |
| `builds-on`    | from is a layer above to (tier stacking) | `engine` builds-on `platform` |

---

## Referential integrity (what a validator should check)

A conforming `diary.json`:

1. has `entries`, `graph.nodes`, `graph.edges` present (arrays);
2. every `entries[].systems[]` id exists in `graph.nodes`;
3. every `edges[].from` / `edges[].to` id exists in `graph.nodes`;
4. every `nodes[].tier` exists in `tiers` (by `id`);
5. every `nodes[].kind` is in the KINDS set; every `edges[].rel` is in the RELATIONS set;
6. each `nodes[].validator`, when non-null, is a **capability** that should be
   resolvable in `../lego/registry.json` (the visualizer renders a ✓/✗ badge from it;
   a capability with no registry entry renders as "unknown").

`gen-diary.mjs` performs checks 1–3 and warns on violations while rendering `DIARY.md`.
